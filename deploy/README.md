# Qpulse — AWS Deploy Runbook

End-to-end procedure for deploying Qpulse to a single AWS EC2 instance with
HTTPS via Caddy + Let's Encrypt. Time from clean AWS account to live URL: **~1
hour of active work** plus DNS + cert-issuance wait time.

Target architecture:

```
                    https://qpulse.<your-domain>
                              │
                    ┌─────────▼──────────┐
                    │  Caddy :443        │  auto Let's Encrypt
                    │  reverse proxy     │
                    └─────────┬──────────┘
                              │ http://127.0.0.1:8080
                    ┌─────────▼──────────┐
                    │  Qpulse (systemd)  │  on-failure restart
                    │  python -m app.live│  user: qpulse
                    └─────────┬──────────┘
                              │
              ┌───────────────┴────────────────┐
              ▼                                ▼
      outbound WS (Alpaca)        /var/lib/qpulse/qpulse_live.{db,json}
```

## Prerequisites

- AWS account with billing set up
- A domain you control (e.g. yourdomain.com), with DNS where you can add records
- Alpaca paper-trading keys (free at <https://alpaca.markets/>)
- SSH key for connecting to EC2 (existing or new)

## Step 1 — Provision EC2 (~15 min)

1. AWS console → EC2 → Launch instance
2. Name: `qpulse-prod`
3. AMI: **Ubuntu Server 22.04 LTS (HVM, ARM)**
4. Instance type: **t4g.small** (or t3.micro on free tier)
5. Key pair: select existing or create new (`qpulse-key.pem`)
6. Network: default VPC, public subnet, **auto-assign public IP**
7. Security group:
   - Inbound: SSH (22) from your IP, HTTP (80) and HTTPS (443) from anywhere
   - **Do not** open 8080 publicly — Caddy will be the only public-facing port
8. Storage: 8 GB gp3 (default), enable encryption
9. Launch → wait for "running"
10. Allocate Elastic IP → Associate with the instance (so the public IP doesn't change on stop/start)

## Step 2 — DNS (~5 min + propagation)

Add an A record at your DNS provider:

```
qpulse.yourdomain.com   A   <elastic-ip>   TTL 300
```

Verify with `dig qpulse.yourdomain.com +short` or `nslookup`. Wait until it returns the elastic IP before proceeding to step 5.

## Step 3 — Initial bootstrap from your laptop (~5 min)

From the project root on your laptop:

```bash
chmod 600 ~/qpulse-key.pem   # if you created a new key
QPULSE_HOST=ubuntu@<elastic-ip> QPULSE_KEY=~/qpulse-key.pem bash deploy/sync.sh --bootstrap
```

`sync.sh --bootstrap` does three things:
1. `rsync` the repo to `/opt/qpulse` on the server (excludes secrets, runtime files, .git)
2. SSH in and run `deploy/install.sh` as root
3. Tells you the manual steps remaining

## Step 4 — Set secrets on the server (~5 min)

SSH in:

```bash
ssh -i ~/qpulse-key.pem ubuntu@<elastic-ip>
```

Edit the systemd environment file:

```bash
sudo nano /etc/qpulse/qpulse.env
```

Replace:
- `ALPACA_API_KEY=PK...` → your real paper key
- `ALPACA_API_SECRET=...` → your real paper secret
- (`HFT_API_TOKEN` was auto-generated by `install.sh`; keep it as-is — write it down for API calls)

Verify the file is locked down:

```bash
ls -la /etc/qpulse/qpulse.env
# expect:  -rw-r----- 1 root qpulse ...
```

## Step 5 — Configure Caddy (~3 min)

```bash
sudo nano /etc/caddy/Caddyfile
```

Replace:
- `qpulse.example.com` → `qpulse.yourdomain.com`
- `YOUR_EMAIL@example.com` → your contact email (Let's Encrypt notification address)

## Step 6 — Start services (~30 sec + cert issuance ~1 min)

```bash
sudo systemctl start qpulse caddy
sudo journalctl -u qpulse -f
```

You should see:
```
[env] loaded /etc/qpulse/qpulse.env  (well, no — systemd already injected it)
[sqlite] persisting alerts → /var/lib/qpulse/qpulse_live.db
[config] loaded persisted overrides from /var/lib/qpulse/qpulse_live.json   (second+ run only)
INFO:     Uvicorn running on http://127.0.0.1:8080
```

Caddy fetches a Let's Encrypt cert on first request. Watch with `sudo journalctl -u caddy -f`.

## Step 7 — Smoke test (~2 min)

From your laptop:

```bash
# Health endpoint (no auth required)
curl https://qpulse.yourdomain.com/health | jq .

# Authenticated /config
TOKEN="<paste HFT_API_TOKEN from step 4>"
curl -H "Authorization: Bearer $TOKEN" https://qpulse.yourdomain.com/config | jq .

# Open the UI in a browser
open https://qpulse.yourdomain.com/
```

Tape should populate within 30s of opening the browser tab.

## Operations

### Update code

```bash
QPULSE_HOST=ubuntu@<elastic-ip> QPULSE_KEY=~/qpulse-key.pem bash deploy/sync.sh
```

This rsyncs the new code and restarts the systemd unit. Persistent state (`qpulse_live.db`, `qpulse_live.json`) is preserved.

### Tail logs

```bash
sudo journalctl -u qpulse -f          # qpulse stdout/stderr
sudo journalctl -u caddy -f           # cert issuance, request log
sudo tail -F /var/log/caddy/qpulse.log   # access log (if configured)
```

### Restart

```bash
sudo systemctl restart qpulse
```

### Inspect persistent state

```bash
sudo -u qpulse sqlite3 /var/lib/qpulse/qpulse_live.db \
    "SELECT kind, COUNT(*) FROM alerts GROUP BY kind ORDER BY 2 DESC"
```

### Backup the SQLite

```bash
sudo cp /var/lib/qpulse/qpulse_live.db /var/lib/qpulse/qpulse_live.db.$(date +%Y%m%d).bak
# or take an EBS snapshot from the AWS console (better — atomic)
```

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `curl https://...` hangs / returns 502 | qpulse isn't running | `sudo systemctl status qpulse` and check journalctl |
| Cert fails to issue ("unable to obtain authorization") | DNS hasn't propagated; or port 80/443 blocked | `dig qpulse.yourdomain.com +short` should return the elastic IP. Check security group has 80 + 443 open |
| `[alpaca] auth failed` in logs | Wrong API keys | Re-check `/etc/qpulse/qpulse.env` matches your paper-account keys |
| Tape stays empty for several minutes | Outside US market hours on IEX feed | Switch to crypto via the Settings UI, or wait for market open |
| Single Alpaca connection limit | Another qpulse / alpaca_check is running with same keys | Kill the other; only one concurrent stream per account on free tier |
| `journalctl -u qpulse` shows ImportError | Dependencies didn't install | SSH in, `cd /opt/qpulse && /opt/qpulse/.venv/bin/pip install -r services/hft_anomaly_service/requirements.txt` |

## Hardening checklist (before sending the URL to anyone external)

- [ ] `HFT_API_TOKEN` is set in `/etc/qpulse/qpulse.env` (not the placeholder)
- [ ] Security group: inbound 8080 is **closed** (only 80, 443, 22 open)
- [ ] SSH from your IP only (or via SSM Session Manager — better)
- [ ] EBS encryption enabled on the volume
- [ ] CloudWatch alarm on instance status / CPU saturation (optional)
- [ ] Daily EBS snapshot lifecycle policy (~$0.05/mo)

## Tear-down

If you want to destroy everything:

1. AWS console → EC2 → terminate instance
2. Release the Elastic IP (otherwise small charge for unattached IPs)
3. Delete the EBS snapshot lifecycle policy if you set one
4. Optionally delete the Route 53 hosted zone
